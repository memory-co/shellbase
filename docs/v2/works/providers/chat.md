# 对话 provider

```python
ChatSpec(id, source, split)  →  Instance(window_url=None, handle=<source 的把手>)
```

## 一个实例 = 另一个实例上的一层轮次视图

它**不调 muxd，也不起任何东西**。`source` 是一个已经存在的实例（通常是
[终端](terminal.md)），对话 provider 拿它的把手，把字符流按 `split` 切成轮次。

所以：**对话与它的 source 是同一份现场**。终端块里滚动的输出，就是对话块里正在
生成的那一轮——不是两份数据的同步，是同一份数据的两种画法。

这也是[三层模型](../protocol.md)里「provider 减少 plugin 开发量」最实的一处：
`claude://` 已经能在终端里跑，要多一个对话形态，plugin 多写的只有那条 `split`。

## 前提：source 必须有把手

只有窗、没有把手的实例（[自定义](custom.md) provider 报的那扇窗就是这样）**接不上**，
`get()` 直接拒绝，而不是给一个空对话框让人对着它发呆。

## `split` 的契约

```python
def split(text: str) -> list[Turn] | None:
    """把一段 scrollback 切成轮次。切不出来返回 None。"""
```

- **切不出来就返回 `None`**，画布据此降级为整屏文本并标一条 note。
  **不猜边界**——给一个错的轮次划分，比给一整块未切分的文本更糟，因为人会信它；
- 规则由 plugin 给，provider 不内置任何启发式。provider 连「提示符长什么样」
  都不该知道。

## 历史从哪来

**source 的 scrollback，对话 provider 不自己存一份。** 两份历史迟早对不上，
而且 scrollback 本来就是[为回看而设计的](../muxd-spec.md)（M10：有上限、能回看、
人能直接读懂）。

代价：**历史长度受 tmux `history-limit` 限制**，滚出去的轮次就没了。要更长的历史，
调那个参数，而不是在这层加一个数据库。

## 拉还是推

**先拉。** tmux 没有原生的「有新输出了」推送，所以对话 provider 在块可见时轮询
`capture()`（200ms 级），不可见时停。

这是权宜，不是设计终点：**轮询的代价是延迟和无谓的抓取**，等 tmuxd 那边有了订阅
接口就换过去。写在这里是为了让它是一个可以被指出来的事实，而不是一个悄悄的实现选择。

## 发送

`send(text, enter=True)` 直接进 source。因此：

- **发出去的内容会原样出现在终端里**，包括手滑发的空行——这是「同一份现场」的代价；
- **没有「撤回」**。对话框里删掉一行不会把已经敲进终端的东西收回来。

## 做不到的

- **没有结构化输出**。它是在字符流上切轮次，不是走 SDK 的消息协议。要结构化，
  得让 plugin 直接调 SDK——那样就与终端形态不再是同一份现场，是另一个取舍；
- **分不清「程序输出」与「人输入的回显」**，除非 `split` 自己能分；
- **不支持并发多轮**。一个 source 一次一轮，前一轮没跑完就发下一段，等于往终端里
  抢着打字。
