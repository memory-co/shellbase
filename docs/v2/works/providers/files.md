# 文件浏览器 provider

```python
FilesSpec(id, root)  →  Instance(window_url=None, handle=None)
```

## 一个实例 = 一次浏览现场，即用即弃

它是五种里**唯一没有活体的**：背后没有 muxd、没有进程，只有平台自己的文件 API
（[v1 files](../../../v1/api/files.md)）。所谓「实例」只是一个句柄，让接口保持一致。

于是三条规则在这里退化成：

- `alive()` **恒真**——只要 root 还在；
- `close()` **无操作**；
- `reap()` **立即可收**，不进保留期的账。关块就是关了，重开只是重新读一遍目录。

**为什么还保留实例形态**：让 plugin 和画布对五种形态用同一套调用方式。
为了「这一种没有状态」而在接口上开个特例，代价比这个空壳大。

## 窗与把手都没有

没有窗，因为不需要——**画布直接渲染树和内容**，用的就是平台的文件 API。
没有把手，因为没有「程序驱动它」这回事：要程序去动文件，直接调文件 API 或走终端，
不必绕这一层。

这说明了 [protocol.md §5](../protocol.md) 那句话：**provider 是呈现契约，不是组件的包装**。
一个 provider 背后完全可以没有组件。

## 边界

root 之外一律拒绝，`resolve()` 之后必须仍在 workspace 根下，符号链接解析后同样受约束
（[v1 files](../../../v1/api/files.md)）。**这条不因为换了协议层就松动**——
它是 v1 就定下的安全边界。

## 变更推送

复用 v1 的 `WS /api/files/watch`：终端里改了文件，文件块立刻能看见。
这也是 shellbase 从一开始就有的那条承诺——**所有子系统共享同一个 workspace**。

## 失败长什么样

| 情况 | 怎么说 |
| --- | --- |
| root 不存在 | plugin 的 `parse()` 该先拦（[file:// plugin](../plugins/file.md)） |
| root 被删了 | `alive()` 转 false，块里说「这个目录没了」，不静默退到上级目录 |
| 越界 | 403，说清楚是越界，不是「找不到」 |

## 做不到的

- **不是编辑器**。能改（mtime 乐观锁），但没有 vim 的键位、没有多光标、没有插件——
  要那些用 [`vim://`](../plugins/vim.md)；
- **大目录会慢**。树按需展开，但单层几万个条目仍然卡，没有分页设计；
- **没有「活得比连接久」**。它本来就没有活体，所以这条对它不适用——
  这是唯一一个 M6 不适用的 provider，写出来免得被当成缺陷。
