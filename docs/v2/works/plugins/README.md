# plugins · 每个协议一个目录

一个 plugin 就是一个协议的实现。三层模型见 [../protocol.md](../protocol.md)，
这里是每个协议各自的声明与判断。

## 总览

| 协议 | 终端 | 网页浏览器 | 对话 | 文件浏览器 | 自定义 | 默认形态 | 会话 |
| --- | :-: | :-: | :-: | :-: | :-: | --- | --- |
| [`claude://`](claude/) | ✓ | | ✓ | | | 终端 | 每块一个 |
| [`vim://`](vim/) | ✓ | | | | | 终端 | **同 path 共享** |
| [`https://`](https/) | | ✓ | | | | 网页浏览器 | 每块一个 |
| [`file://`](file/) | | | | ✓ | | 文件浏览器 | **无会话** |
| [`bash://`](bash/) | ✓ | | | | | 终端 | 每块一个 |

三处偏离默认的地方，都是 plugin 该自己拿主意的例子：

- **`vim://` 同 path 共享会话**——两个 vim 编辑同一个文件会打架（swap file），
  所以它在 `session_id()` 里去掉 block 号；
- **`file://` 没有会话**——文件浏览器背后没有长驻进程，`session_id()` 返回 `None`，
  画布层就不去向组件要 session；
- **`bash://` 兼任兜底**——没有 plugin 认领的 scheme 落到它，scheme 名即命令名。

## 一个新 plugin 的文档要回答什么

五个问题，答不出就先别写代码：

1. **path 是什么**，怎么校验，校验失败怎么说；
2. **支持哪几种形态**，各自怎么接线（每种 provider 要什么，见 [protocol.md §3](../protocol.md)）；
3. **会话怎么算**——每块一个、同 path 共享，还是根本没有会话；
4. **依赖什么**，不满足时报什么（必须带这台机器上的那条命令，[M12](../muxd-spec.md)）；
5. **哪些做不到**——诚实写下来，而不是等用户撞上。

## 目录形状

每个协议一个目录，先只有 `README.md`；某个协议的某一面复杂到值得单开一篇时
（比如对话形态的轮次协议），就在它自己的目录里加文件，不往上挤。
