# `claude://` · 在一个目录上开工

```
claude:///workspace/proj      在这个目录上开工
```

形态不写在 URI 里（[protocol.md §4](../protocol.md)）：默认起终端，
块里的切换入口由本 plugin 自己提供，切过之后记在块状态里。

这是**最能说明 provider 分层价值**的一个：它本来就是终端程序，终端形态零成本；
多一个对话形态，只多写一条切轮次的规则。

## path

工作目录。**不存在就建；但父目录不存在则报错**——「在新目录开工」是常见起手式，
而一路 `mkdir -p` 下去只会把手滑打错的路径变成一棵深目录树。

## 形态

| | 接线 |
| --- | --- |
| **终端**（默认） | 向 tmuxd 要 session：`cwd=path`、`cmd=claude`；窗由组件报出 URL |
| **对话** | 同一个 session 的 `send()` / `capture()`，外加切轮次的规则 |

**两种形态共用同一个 session**，所以终端块里滚动的输出和对话块里的最后一轮是同一件事；
也因此，用户可以一边在对话里发指令、一边在终端块里看它到底敲了什么。

### 切轮次的规则

以「一次输入的回显」到「下一次出现输入提示」之间为一轮。**这是启发式，会错**——
claude 的输出里可能出现形似提示符的内容。所以：

- 切不出轮次时**降级为整屏文本**，并在那一轮上标一条 note，说明「没能切分」；
- **不猜**——不做「看起来像回答就当成一轮」这类推断。宁可给一整块，也不给一个错的边界。

轮次历史来自 tmux 的 scrollback（[M10](../muxd-spec.md) 日志即 scrollback），
plugin 自己不再存一份——两份历史迟早对不上。

## 会话

沿用默认：身份含 window 与 block，**同一个目录可以开多个 claude**。
这是有意的：一个块跑长任务、另一个块问东西，是常见用法。

## 依赖与凭据

- `claude` 要在 PATH 里。不在就报出装它的那条命令（[M12](../muxd-spec.md)），
  而不是「命令未找到」；
- `ANTHROPIC_API_KEY` 由平台的全局环境变量机制注入（[v1 env](../../../v1/works/env.md)），
  plugin 不自己管凭据。

## 做不到的

- **对话形态没有真正的结构化输出**。它是在字符流上切轮次，不是走 SDK 的消息协议。
  想要结构化，得换一条实现路径（plugin 直接调 SDK，不经 tmux）——那样就与终端形态
  不再是同一份现场，是另一个取舍，现在不做；
- **对话里发出去的内容会原样进入终端**，包括手滑发的空行。这是「同一份现场」的代价。
