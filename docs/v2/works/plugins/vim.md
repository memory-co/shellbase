# `vim://` · 编辑一个文件

```
vim:///workspace/a.py        编辑这个文件
vim:///workspace/proj        在这个目录里开 vim
```

## path

**必须已经存在**。文件就打开它，目录就在里面开 vim。

为什么不像 `claude://` 那样「不存在就建」：编辑器打开一个不存在的路径，用户的意图
八成是打错了字，而不是要新建。真要新建，`vim` 里 `:e` 一下比在 URI 上手滑更可控。

## 形态

**只有终端。** 这不是缺憾——vim 就是一个终端程序，它的键位、`.vimrc`、插件全都活在
终端语义里。

**为什么不给它一个「网页编辑器」形态**（比如 code-server）：那会改变协议的语义。
在 code-server 里编辑同一个文件，键位、配置、插件全都不是 vim 的那一套——**那是另一个
协议（`code://`），不是 vim 的另一种形态**。[protocol.md §2](../protocol.md) 那条硬约束
在这里就是这么用的。

## 会话

**同 path 共享一个会话**——`session_id()` 里去掉 block 号。

理由很实在：两个 vim 编辑同一个文件会打架，第二个进来只会看到一句 swap file 警告。
与其让用户自己撞上，不如让第二个块直接接上第一个块的那份现场。

这也是[三层模型](../protocol.md)里「会话身份归 plugin 决定，画布层不猜」的样板：
默认（每块一个）对终端合适，对编辑器就是错的。

## 依赖

`vim` 在 PATH 里。不在就报出装它的那条命令。

## 做不到的

- **多个块看同一个 vim，是同一份现场而不是各看各的。** 一个块里滚屏，另一个块跟着滚——
  这是 tmux 多客户端的固有行为（[v1 collab](../../../v1/works/collab.md)）。想各看各的，
  开两个不同的文件；
- **不接管 vim 的退出**。用户 `:q` 之后会话就空了，块里是个退出后的 shell。
  要不要在这种时候自动关块，是画布层的产品决定，不是协议层的事。
