# 一种新的界面 · HTTP 上的一扇窗，加一个能控它的把手

> 这篇讲的不是某一个项目，是 `tmuxd` 和 `webmuxd` **共同属于的那个东西**：
> 它们从哪来、为什么长成同一个形状、为什么是两个项目而不是一个。
> 可检查的判据在 [muxd-spec.md](muxd-spec.md)，这篇只讲为什么。

## 1. 从哪来：shellbase 剩下的那两块

shellbase 是一块可自由分割的画布，把终端、浏览器、文件融进同一屏（[v1 设计](../v1/works/design.md)）。
它 v1 里有两处「先欠着」：

- **终端**是网关后面反代的一个 ttyd，ttyd 挂在 tmux 上。能用，但那是**拼在架构里的**，
  不是一个能单独拿出来的东西；
- **浏览器面板是纯前端 iframe** —— v1 的原话是「容器内 headless 浏览器留给 v2」，
  也就是说那一块当时根本没做。

共同点是：**它们都不该是某个产品的内部零件。** 一个活着的终端、一个能被人和程序同时
用的浏览器，是两种独立成立的能力。留在 shellbase 里的后果是：别人想要一个持久终端，
得把整个工作台搬走；我们自己想换浏览器实现，得动网关。

所以抽出来，成了 `tmuxd` 和 `webmuxd`。shellbase 从「自己实现」变成「**组织展示**」——
仍然是那块画布，但每个块背后是一个独立模块。

## 2. 共同的形状：一扇窗 + 一个把手

```
一扇窗    HTTP 上的一个端口      ← 人打开就能看，而且能直接上手
一个把手  Python 里的一个对象    ← 程序驱动它
                  ↑
             同一个东西
```

`tmuxd` 的窗是 ttyd 的端口，把手是 `Session.send()`；`webmuxd` 的窗是 VNC 的端口，
把手是 `Tab.click()`。**除此之外它们没有共享任何一行代码。**

**窗为什么必须在 HTTP 上**——不是「顺便支持浏览器」，是只做浏览器：分享就是发一个 URL，
不用装客户端、不用配 SSH key；人和程序看的是**同一块而不是两份状态**，程序点了什么人
立刻看见，人伸手改了什么程序下次就读到；窗活得比连接久，关掉网页里面照常在跑。

**把手为什么必须是库**——大多数调用方（编排程序、Web 后端、脚本）本来就和它在同一个
进程里，让它们绕一圈 HTTP 去调自己进程里就能做的事，是白交的税。所以 `pip install`
完就能用，不需要先起 server：

```python
t = Tmuxd(port=12345);  s = t.session(id="work");             s.send("跑测试", enter=True)
w = Webmuxd();          s = w.session(id="work", port=7900);  s.open(url).click("提交")
```

## 3. HTTP API 存在的唯一理由：让模块能被独立验证

这条要写死，因为它决定了 API 的所有取舍。

**API 不是给外部当产品用的。** 它存在，是为了让模块**不依赖任何上层、不 import 任何
调用方代码**就能证明自己是对的：

```bash
webmuxd new -s demo -p 7900 && webmuxd click -t demo "提交订单"
curl -s localhost:7900/api/tabs | jq
```

一个只能在集成环境里被证明是对的模块，还没有真的独立出来。由此推出三条：

1. **API 不做库没有的事。** 反过来可以——`with` 自动清理、`obs[12]` 下标这类纯客户端
   的便利，导出去没意义；
2. **API 不必优雅。** 读者是调试的人和验证脚本，不是产品用户。为它做版本兼容、
   SDK 生成、OpenAPI 美化，都是错配的投入；
3. **上层不该被迫走 API。** 正确用法是 `import`。API 在那儿，是为了让「不 import 也能
   验一遍」这件事永远成立。

非 Python 集成仍然能用，但那是**顺带**，不是理由。

## 4. 三种包法，同一个规范

| | 包的是 | 例子 |
| --- | --- | --- |
| **一个进程** | 一个现成的服务端 | tmuxd 的 ttyd |
| **多个进程** | 自己拼一套 | webmuxd 的 `process` runtime：chromium + Xvnc + sessiond |
| **多个镜像** | 别人做好的整机 | webmuxd 的 `container` runtime：kasmweb / jlesage / linuxserver |

**「包多个镜像」最有意思**：窗那一半整个是别人的产品，我们只挑一个、把端口报出来。
挑的依据是体验，换的时候**我们一行都不改**——因为窗不在契约里。

三种没有优劣，只是被包的东西成熟度不同。规范管的是它们对外长什么样，不是里面怎么实现。

## 5. 为什么是两个项目，不是一个

**因为共享的只是形状，不是代码。** 底下差得太远，合成一个的结果是一个到处
`if kind == "term"` 的框架，而不是一个更强的东西。

| | tmuxd | webmuxd |
| --- | --- | --- |
| 契约那一半 | `tmux` 命令行 | **CDP**（WebSocket 协议） |
| 状态在哪 | tmux server 自己管，我们只发命令 | 我们**自己维护一份 tab 表**，靠事件流对齐 |
| 驱动方式 | `send-keys` 一句话 | 定位 → 动作 → 等待稳定 → 观测，四段 |
| 「看见」是什么 | `capture-pane` 拿文本 | AX 树 + 标注截图，喂多模态模型 |
| 窗那一半 | ttyd，一个静态二进制 | 一整个桌面镜像（4 GB 级） |
| 最难的地方 | 依赖怎么装（ttyd 不在多数发行版仓库里） | **CDP 怎么出容器**（Chromium 只肯听 loopback） |
| 失败长什么样 | 进程没了 | 页面卡住、元素找不到、截图超时 |

**唯一真正共享的是那份规范**——而规范应该长在文档里，不是长成一个基类。反面例子：
强行统一的话，`Tab` 和 `Pane` 得抽象成同一个「块」，而它们唯一的共同点是「有个 id」；
为这点共性付出的代价是两边都要迁就那个抽象。

## 6. 下一个成员会长什么样

这个形状不止能装终端和浏览器。任何**「人要看着、程序要驱动、而且得活着」**的东西都能
套进来——一个文件工作区、一个数据库客户端、一个笔记本内核。新成员进来只需回答三问：

1. 窗是什么？（哪个现成的 web 服务端能当它）
2. 把手是什么？（哪个协议 / 命令行能驱动它）
3. 这两者里，**哪一半是用户会直接碰到的**？（那半就是契约）

答不出第 3 条，就还没想清楚该抽什么。
